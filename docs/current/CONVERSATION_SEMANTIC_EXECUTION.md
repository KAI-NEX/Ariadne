# 对话理解与执行架构

更新：2026-09-09。范围：共用的人类意图理解原则，以及 Candidate 对话的字段选择、批量修改、澄清、执行回执和分类标签。不是通用电脑操作 Agent，也不更换 Provider/model。

## 问题原因

过去混淆了三个不同职责：模型理解用户表达、代码解析存储目标、界面解释操作结果。批量范围用当前句的固定词匹配，承接上一轮的“就这样改”容易被拒绝；模型的具体澄清被固定追问覆盖；类别并非可编辑字段，却被解释为用户没有说对字段。单张卡片的成功回执又重复“这张卡片”，不能说明批量改了谁。

## 当前分层

| 层 | 职责与边界 |
| --- | --- |
| 共用理解原则 | `src/conversation_semantics.py`：区分讨论、提问、事实补充、执行授权和取消；理解指代、排除、纠正及承接；只问真正缺失的信息。Candidate、Job、个人理解、职位概况共用，但不共享写入权限。 |
| 当前观察与能力目录 | 每轮绑定同源 Working 指纹、版本及焦点。Candidate 向模型提供当前卡片及 `editable_fields`：可读标签、当前值、允许操作和临时字段引用。代码生成目录，不让模型猜内部字段 ID。 |
| 模型语义计划 | 模型把用户概念映射至当前卡片/字段。`field_ref` 属于本轮、当前卡片；它避免要求“就读时间”必须逐字等于“日期”。原 concept adapter 继续兼容既有调用。 |
| 范围依据 | 新批量计划引用当前用户原话；承接时还引用同一有界上下文内的历史用户原话。前后端核对引用，不把助手建议、来源材料或其他会话当作授权。模型负责判断语义；原话存在不能单独证明语义正确。旧的无引用 canonical action 保留原有当前句限制，避免扩大旧数据权限。 |
| 解析与校验 | 只将已有卡片/字段映射为类型化操作；拒绝未知引用、非法操作、越过焦点、过期观察及版本冲突。字段引用已经明确时，不再二次用自然语言 selector 做逐字匹配。 |
| Working 与回执 | 批量一次形成新的 Working 版本，非目标项不变。逐项读取结果核对后，由实际回执显示卡片标题、字段与前后值；长文本缩略仅影响回执，不截断实际修改。历史携带实际操作结果，避免把“讨论过”当“执行过”。 |
| Human Save | 仍由用户点击保存生成确认版本；来源、旧 Working、旧确认版本与历史消息保留。普通对话不会自动确认资料。 |

## 分类标签

Candidate item 新增可选 `category`（最多 120 字符）。单张卡片一个分类标签，可添加、替换、清空。未设置时仍显示原来的工作经历/项目经历/教育经历说明；设置后在卡片说明位置显示自定义分类。底层 `item_type/item_subtype` 和栏目分组不变。

字段贯穿对话、Working、手动编辑、修改预览、确认保存、同源恢复、个人/JD 上下文和差异识别；不清空数据库或批量迁移旧记录。不将“建筑项目”写死为规则，不把分类标签当作能力证明。

## 用户怎么操作

1. 更新服务后刷新原来的浏览器页面，打开资料的候选人工作区。需要跨卡片修改时回到全部卡片列表。
2. 直接说明要达到的结果，例如“除了声音实验，其余项目标为研究项目”“这段经历我的角色是研究协调，标题不变”“学校的就读时间改成 2024–2026”。也可以在已明确范围后说“就这样改”。
3. 核对左侧卡片与回复中的实际变化。只想讨论时说“先解释，不要改”；最新的取消或纠正优先。
4. 满意后点击“保存到个人资料”。单卡“编辑”也能填写或清空分类标签；清空后恢复默认类型说明。

## 保留的限制

- 模型理解仍有出错可能；引用、schema 和版本校验不能替代语义验收，因此仍提供可核对的草稿及人工保存。
- Candidate 对话不新增/删除/合并卡片、不新增事实行、不跨来源修改；新增事实可使用既有手动编辑。多标签、跨来源批量编辑和任意系统操作未实现。
- ITEM_DRAFT 不能越过当前卡片；其他领域不因共用提示而获得 Candidate 写权限。个人理解仍只能提出可审阅的个人补充；职位概况仍只读职位集合。
- 真实模型测试与模拟传输 UI 测试分别记录，不将测试替身算作模型能力证据。测试使用合成数据，不修改用户真实资料。
